  Bug #6: FIN Not Detected if Not in Maximum Sequence Segment 
  (segment.ml:103-105)

  Location: /Users/svanders/nethsm/mirage-tcpip/src/tcp/segment.ml:103-105

  let fin q =
    try (S.max_elt q).header.fin
    with Not_found -> false

  The Problem: The fin function only checks if the MAX element (highest
  sequence number) has the FIN flag. If a segment arrives with FIN, but then
   another segment arrives with a higher sequence number (which violates TCP
   but could happen with a buggy/malicious sender), the FIN won't be
  detected at all!

  Example scenario:
  - Receive segment 1: seq 100-109, has FIN flag
  - Receive segment 2: seq 110-119, no FIN (illegal data after FIN)
  - Both are in-sequence and added to the ready set
  - fin(ready) checks the max element (segment 2) → returns false
  - FIN is never processed, connection never closes!

  Note: The developers acknowledge this in the TODO comment (lines 100-102):
   "should look for a FIN and chop off the rest of the set as they may be
  orphan segments"

  Bug #7: TIME_WAIT Timeout Way Too Short (state.ml:96)

  Location: /Users/svanders/nethsm/mirage-tcpip/src/tcp/state.ml:96

  let time_wait_time = (* 30 *) Duration.of_sec 2

  The Problem: TIME_WAIT state only lasts 2 seconds! According to RFC 793,
  TIME_WAIT should last 2*MSL (Maximum Segment Lifetime). The standard MSL
  is 2 minutes, so TIME_WAIT should be 4 minutes (240 seconds), not 2
  seconds!

  Why this matters: TIME_WAIT exists to ensure that:
  1. Any delayed segments from the old connection arrive and are discarded
  before the port can be reused
  2. The final ACK has time to be retransmitted if it's lost

  With only 2 seconds, the same port pair could be reused too quickly, and
  delayed segments from the old connection could be mistaken for the new
  connection's data!

  Note: The comment says (* 30 *) suggesting someone intended 30 seconds,
  but even that's too short.

  Bug #8: FIN_WAIT_2 Timeout Resets on Every ACK (state.ml:98-113, 154)

  Location: /Users/svanders/nethsm/mirage-tcpip/src/tcp/state.ml:98-113 and
  line 154

  let rec finwait2timer t count timeout =
    ...
    match t.state with
    | Fin_wait_2 i ->
      if i = count then begin
        t.state <- Closed; ...
      end else begin
        finwait2timer t i timeout  (* Timer restarts! *)
      end

  And:
  | Fin_wait_2 i, Recv_ack _ -> Fin_wait_2 (i + 1)

  The Problem: Every time an ACK is received in FIN_WAIT_2 state, the count
  increments. When the timer fires, it sees the count has changed and
  restarts the timer!

  Attack scenario:
  - Attacker causes connection to enter FIN_WAIT_2 (we sent FIN, it was
  ACKed)
  - Attacker sends ACKs continuously (duplicate ACKs, ACKs with data,
  keepalives, etc.)
  - Each ACK increments the count, causing the FIN_WAIT_2 timer to restart
  - Connection stays in FIN_WAIT_2 indefinitely, never timing out!

  This could be used for a resource exhaustion attack - keep many
  connections stuck in FIN_WAIT_2 forever.

⏺ Perfect! Bug #10 is now fixed. Here's a summary:

  Bug #10 Fixed: FIN Processing Blocked by Full User Buffer

  The Problem You Observed

  Under busy conditions:
    Incoming FIN → ACKed ✓
    Response FIN → Never sent ✗
    Connection stuck in ESTABLISHED

  Root Cause

  The code delivered FIN processing in two separate steps:
  1. Deliver data → ACK sent (including FIN acknowledgment)
  2. Deliver FIN indication → State transitions to CLOSE_WAIT

  If the user buffer was full between steps 1 and 2, the code would block 
  waiting for buffer space, preventing step 2 from executing. The state
  never transitioned, so no response FIN was sent.
