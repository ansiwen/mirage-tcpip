⏺ Excellent! The fix is now correct. The issue was a race condition in the 
  mvar queue:

  Root Cause

  When data arrived with delayed=true, Ack.receive would immediately call
  transmitack, which queued the ACK into the send_ack mvar. Then when the
  server sent response data with a piggybacked ACK, ACK.transmit updated
  last_sent_ack, but the pure ACK was already queued in the mvar and would
  be sent anyway (5μs later in your pcap trace).

  The Fix

  The critical insight: check last_sent_ack BEFORE queueing into the mvar
  (in transmitacknow), not after. Only ACK.transmit updates last_sent_ack
  when ACKs are actually transmitted.

  Now the flow works correctly:
  1. Data arrives → transmitack tries to queue ACK
  2. transmitacknow checks last_sent_ack=None, queues ACK
  3. Server sends piggybacked ACK → ACK.transmit updates last_sent_ack=689
  4. If timer fires or more data arrives → transmitacknow checks
  last_sent_ack=689, skips queueing duplicate

  All 409 tests pass! Bug #16 is finally fixed correctly.

  The Complete Fix

  Your insight was exactly right - we should check and update last_sent_ack
  as late as possible. But we also need to distinguish between:

  1. Normal delayed ACKs (from receive()) → Can skip if duplicate
  2. Forced ACKs (from pushack()) → Must ALWAYS send, even if duplicate

  Implementation

  In ack.ml:
  - transmitacknow: Checks last_sent_ack before queueing → skips duplicates
  - pushack: Directly queues into mvar without checking → always sends
  - transmit: Updates last_sent_ack when ACK is transmitted

  This ensures:
  - The race condition duplicates are eliminated (delayed ACK vs piggybacked
   ACK)
  - Challenge ACKs for RFC5961 security features are always sent
  - All 409 tests pass!

  The check happens in transmitacknow right before queueing (as late as
  possible before entering the mvar queue), and last_sent_ack is updated in
  transmit when the ACK is actually transmitted (as late as possible).
